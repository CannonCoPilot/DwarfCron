XRig runs to check the fixes and watch the processes

Ten run designs on four saved forts that already exist, plus three forts to make. One run kit records every run the same way, so each run doubles as a monitor of wildlife behaviour and of the tool's own processes. Screening runs use 3 replicates; a run that decides a ruling uses 5. About 22 rig hours in all, most of it in unattended overnight chains.

The run kit (build first)

Today the v7.3 season tooling is a set of scripts with no single driver. One driver, season-run, will do for every run:

  1. Load a backed-up fort by folder (never the original), with a per-chunk timeout.
  2. Receipts first: the fort's casts, settings and the manipulation under test are read back and the subject is proven on the map; any failure aborts the cell (manifest-subject rule).
  3. Record: the in-game recorder (arrivals, departures, attacks, kills, deaths, positions every 100 ticks) and the tool's ledger captured live (its buffer keeps only 300 lines), plus ecology pairs tsv and cast status every 3,000 ticks.
  4. Step in 20,000-tick chunks, saving each (DF hangs about every 40-60k ticks at speed), watering and feeding the dwarves each chunk (rig embarks carry no drink).
  5. Dump and analyse: one JSON per cell (v73_check, f0_compare and the food-web graph), then the season-test page rebuilt and republished.

  5. X9, the one-year run, on the release candidate; then F22, release 7.3.0.

Rules every run follows

  • A fresh load per cell; the order of arms reversed on even replicates.
  • DF restarted between arms on long runs (one process loses up to 28% speed over 300k ticks).
  • Arms of a frame-rate comparison paired inside one session (identical loads differ by 10-16%).
  • A run that comes back thin (too few subjects) is marked pending, not re-fixed mid-round.
  • Counts are by the unit's own population source and the tool's group, never by DF's wave flag alone (readout traps 29-34).
